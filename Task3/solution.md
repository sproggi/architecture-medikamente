# Задание 3. Оценка Data Encryption at Rest and In Transit

Система: «Медикаменте», целевая (To-Be) архитектура из Task2. Задача — стратегия шифрования данных во всех состояниях: **at rest** (при хранении), **in transit** (при передаче), кратко — **in use** (в обработке). Связь с предшествующими заданиями: закрывает **ПЗ-4** (нет шифрования at-rest и in-transit), риски **R2, R3, R9, R10, R11, R12** (Task2 §3), требования 152-ФЗ (ст. 18.1, 19), PCI DSS 4.0 (платежи) и 54-ФЗ (фискальные данные).

---

## 1. Состояния данных и периметр оценки

| Состояние | Что защищаем | Примеры в системе |
|---|---|---|
| **At rest** | Данные на дисках, в БД, объектных хранилищах, бэкапах, на носителях | PostgreSQL (OLTP), ClickHouse (curated), 1С (ИБ), MinIO (сканы, договоры), Elastic (логи), raw-зона (MinIO Object Lock), бэкапы, SSD/HDD |
| **In transit** | Данные в каналах: клиент, сервисы, интеграции | Портал/мобилька ↔ API GW, сервис ↔ сервис (Istio), сервис ↔ БД/Kafka, ККМ ↔ 1С, 1С ↔ 1С, API лаборатории, платёжный шлюз, налоговая, Exchange, SMS/голос, CDC (Debezium), перемещение бэкапов |
| **In use** | Данные в памяти и на экранах при обработке | Сессии врачей/ресепшена, UI порталов, логи, выгрузки, LLM-ответы (маскирование, непродолжительное хранение, без записи PII в логи) |

Периметр: все 16 категорий данных из Task1 §3 + производные (BI/ML/LLM). Локализация ПДн — РФ (ст. 18 ч.5 152-ФЗ): все ключи и данные — в инфраструктуре на территории РФ.

## 2. Классификация данных: состояние × чувствительность × профиль риска

Классы чувствительности: **ОСОБ** — особая категория (ст. 10 152-ФЗ, здоровье); **PII** — персональные данные; **ФИНА** — финансовые (PCI DSS, 54-ФЗ); **СОТР** — ПДн сотрудников; **СЕКР** — ключи/учётные данные; **МЕТА** — логи и метаданные; **КОММ** — коммерческая тайна.

| № | Данные | Класс | At rest (где лежит) | In transit (какие каналы) | Профиль риска (угрозы, Task2 §3) | Критичность |
|---|---|---|---|---|---|---|
| 1 | Медкарты, диагнозы, заключения врачей | ОСОБ | PostgreSQL (TDE), MinIO (сканы) | Портал TLS, сервис mTLS, CDC Kafka | R1 (врач/ресепшен — чужой пациент), R2 (массовая утечка через учётку), R12 (подмена медкарты) | **Критическая** |
| 2 | Результаты анализов | ОСОБ | PostgreSQL, реестры лаборатории | API лаборатории (mTLS, `x-data-classification`), CDC | R1, R3 (re-identification в BI/ML), R10 (утечка через LLM) | **Критическая** |
| 3 | Сканы медкарт и договоров (JPG/PDF) | ОСОБ + PII | MinIO (SSE-KMS), legacy — файловый сервер | S3-sync в raw, DLP-контроль выгрузок | R9 (скан на личную почту), R12 (целостность документа) | **Критическая** |
| 4 | PII пациента (ФИО, ДР, телефон, email, адрес) | PII | PostgreSQL, CRM, legacy Excel | Портал TLS, mTLS, Kafka, Exchange | R2, R9, R11 (выгрузка базы злостным сотрудником) | **Высокая** |
| 5 | Согласия на обработку (в т.ч. спецкатегорий) | PII + правовое основание | PostgreSQL (Consent Service) | Портал TLS, mTLS | R8 (нет согласия / нет отзыва) | **Высокая** |
| 6 | Договоры (клиентские) | PII + КОММ | PostgreSQL, MinIO | Портал TLS, ЭЦП | R12 (подмена условий/сумм) | Средняя |
| 7 | Платежи, чеки ККМ, PAN карт | ФИНА + PII | 1С:Бухгалтерия, ККМ | ККМ ↔ 1С (TLS вместо OLE), платёжный шлюз (PCI TLS) | R12 (искажение чека/платежа), PCI DSS (несанкционированное хранение PAN) | **Высокая** |
| 8 | Кадровые данные, зарплаты | СОТР | 1С:Бухгалтерия | 1С ↔ 1С (TLS), налоговая (ЭЦП, TLS) | R2, R11 (зарплата — внутрикорпоративный секрет) | **Высокая** |
| 9 | ТМЦ, закупки | Бизнес-данные | 1С:Торговля | 1С ↔ 1С (TLS) | R12 (минимальный) | Низкая |
| 10 | Учётные данные AD/LDAP, ключи, секреты | СЕКР | AD, Vault (Transit/Secrets) | mTLS, PAM-доступ (Teleport) | R2 (компрометация AD = доступ ко всем медкартам) | **Критическая** |
| 11 | Логи аудита C/R/U/D, метаданные | МЕТА | Elastic (WORM), MinIO (raw) | SIEM (TLS) | R6 (неаудируемость), R12 (стирание следов) | **Высокая** |
| 12 | Данные BI/ML/LLM (производные) | Производные PII | ClickHouse (curated), raw-зона | Kafka, LLM-gateway, выгрузки Superset | R3 (re-identification), R10 (утечка через модель) | **Высокая** |
| 13 | Переписка Exchange (в т.ч. с ПДн/здоровье) | PII + ОСОБ | Exchange Mail Server | SMTP/OWA TLS, DLP исходящих | R9 (PII на личную почту/наружу) | **Высокая** |
| 14 | SMS/голосовые уведомления | PII + ОСОБ (контент) | Каналы оператора | API оператора (TLS) | R9 (избыточные данные в SMS) | Средняя |
| 15 | Бэкапы всех СУБД и файлов | Все классы | Бэкап-репозиторий (онлайн + offline) | Перемещение между узлами | R2 (бэкап = полная копия), R12 (подмена бэкапа) | **Высокая** |

## 3. Обоснование необходимости защиты по классам

| Класс | Почему защита необходима | Что произойдёт без шифрования |
|---|---|---|
| **ОСОБ** (здоровье) | Ст. 10, 18.1, 19 152-ФЗ: на спецкатегории распространяются усиленные технические меры; максимальный репутационный и финансовый риск утечки (позиция техдиректора, Task1). R1/R2/R10 | Подглядка в медкарту при краже диска/USB; массовая утечка при компрометации AD; re-identification в аналитике; штраф РКН, суды, уход пациентов |
| **PII** (пациенты) | Ст. 5, 18.1 152-ФЗ; R2/R9/R11: компрометация одной учётки, письмо на личную почту, выгрузка злостным сотрудником | Утечка баз (ФИО+телефон+адрес) → фишинг пациентов, продажи баз, штрафы |
| **ФИНА** (платежи, PAN) | PCI DSS 4.0 (треб. 3 — защита хранимого PAN, треб. 4 — шифрование при передаче); 54-ФЗ — целостность фискальных данных | Штрафы эквайера, блокировка приёмки карт; искажение/двойное начисление платежей (ПЗ-6) |
| **СОТР** (кадры, зарплаты) | 152-ФЗ + режим коммерческой тайны по зарплате; R11 | Утечка зарплат = конфликты, увольнения, репутация |
| **СЕКР** (ключи, учётные) | R2: KEK/секреты — корень всей цепочки; «компрометация AD = всё» (Task1 §2) | Полное раскрытие всех at-rest данных; необратимо |
| **МЕТА** (аудит, lineage) | Ст. 24 152-ФЗ — фиксация операций; R6/R12: доказательная база не должна подделываться | Невозможно ответить регулятору «кто читал медкарту»; злоумышленник стирает следы |
| **Производные** (BI/ML/LLM) | R10: модель «запоминает» PII и выдаёт в ответах; R3: псевдоним без защищённого ключа де-персонимизируется | Утечка через LLM-чат, re-identification по агрегатам |
| **КОММ** (договоры) | Целостность коммерческих условий (R12) | Подмена сумм/условий, правовые споры |

**Вывод:** без шифрования at-rest единственная защита — доступ к носителю/учётке; без шифрования in-transit — единственная защита — периметр сети. Для ОСОБ-данных оба условия несоблюдены (ПЗ-4) → защита обязательна и по закону, и по риску.

## 4. Стратегия шифрования at rest

| Хранилище | Данные | Механизм | Алгоритм | Ключи | Примечания |
|---|---|---|---|---|---|
| PostgreSQL (OLTP) | Медкарты, PII, согласия | TDE: шифрование диска (LUKS2/AES-256-XTS) + **column-level pgcrypto** для полей ОСОБ/PII | AES-256-GCM (колонок), AES-256-XTS (LUKS) | DEK из Vault Transit | RLS (изоляция `patient_id`) — Task2; ключ колонки ≠ ключ диска |
| MinIO (файлы, сканы) | Сканы, договоры | SSE-KMS (server-side encryption via KMS) | AES-256-GCM, уникальный ключ на объект | Vault Transit | DLP на выгрузы (Task2) |
| MinIO Object Lock (raw-зона) | Оригиналы из источников | SSE-KMS + WORM (Object Lock, governance) | AES-256-GCM | Отдельный DEK raw-зоны | Доступ только ETL-сервис; crypto-shredding при истечении retention |
| ClickHouse (curated) | Только обезличенные данные | LUKS2 на дисках; **нативного TDE нет** → двойная страховка: на уровне приложения в зону попадают только псевдонимы | AES-256-XTS | DEK зоны аналитики | Ключи де-персонимизации **не хранятся** в зоне (Task2 §5.2) |
| Elastic (логи, WORM) | Аудит C/R/U/D, lineage | LUKS2/SED-диски + TLS transport; иммутабельность через ILM (WORM-режим) | AES-256-XTS | DEK | Лог не удаляется до конца retention |
| 1С:Бухгалтерия/Торговля | Платежи, кадры, ТМЦ | Перевод на клиент-серверный режим (Task2 ПЗ-8); ИБ на сервере — LUKS2/SED, если СУБД 1С = PostgreSQL — TDE как выше | AES-256 | DEK finance | Файловый режим (As-Is) не даёт контроля доступа — шифрование файла 1С само по себе недостаточно |
| Бэкапы | Все классы | restic/age (или Vеem Enterprise Manager): шифрование контейнера при создании | AES-256-GCM (AGE) | Отдельный DEK backup, ротация; ключ хранится отдельно от бэкапа | Схема 3-2-1 + offline-копия; **автоматическая проверка восстановимости** (restore-тест) |
| Носители (SSD/HDD) | Всё физическое | SED (self-encrypting drive) или LUKS2; при утилизации — **crypto-erase** (сброс ключа носителя) | AES-256-XTS | Ключ носителя | Защита при краже сервера из офиса |
| Legacy-файлы (As-Is, до миграции) | Сканы, Excel | BitLocker (Windows Server 2022) + ограничение общих папок (RBAC) | AES-128/256 (XTS) | Групповые политики AD | Временная мера до переезда в MinIO |

**Иерархия ключей (envelope encryption):**

```
KEK (Master Key) — HSM / Vault, доступ только PAM (Teleport), MFA, принцип 4-eyes
 ├── DEK medical   — PostgreSQL (колонки), MinIO (сканы), raw-зона        ротация 30 дней
 ├── DEK pii       — PII-поля, CRM                                       ротация 90 дней
 ├── DEK finance   — 1С, бэкапы финансового контура, ККМ-контур          ротация 90 дней
 ├── DEK hr        — кадровый контур 1С                                  ротация 90 дней
 ├── DEK logs      — Elastic, WORM-архив                                  ротация 180 дней
 ├── DEK analytics — ClickHouse, датасеты (без ключей ре-идентификации)  ротация 90 дней
 └── DEK backup    — бэкап-контейнеры                                    ротация 180 дней
```

- **Crypto-shredding** (Task2, сценарий С4): удаление данных по ст. 21 152-ФЗ и по retention = уничтожение DEK домена — без переписи данных.
- **Ротация** автоматическая: Vault (Transit key versions) + CI-контроль возраста ключей (п. 7).
- Псевдонимизационные токены `patient_id` — детерминированное AES-256-GCM / HMAC из Vault, ключ — только в Vault (Task2 §5.2, пункт 1).

## 5. Стратегия шифрования in transit

| Канал | Протокол | Требования | Сертификаты | Дополнительно |
|---|---|---|---|---|
| Пациент/сотрудник ↔ портал/мобилька (Web, API) | TLS 1.2 (мин.) — 1.3 (цель) | ECDHE + AES-256-GCM / ChaCha20-Poly1305; HSTS; запрет SSLv3/TLS 1.0/1.1, RC4/3DES/анонимных cipher suite | Vault PKI, срок ≤ 90 дней, мониторинг истечения | WAF на входе; для мобильки — certificate pinning (опция) |
| Сервис ↔ сервис (внутри платформы) | **mTLS** (Istio Service Mesh) | Взаимная аутентификация, короткоживущие сертификаты (1–24 ч), авто-ротация | Istio + Vault PKI (cert-manager) | Часть факторизации P2D (Task2 §4): без mTLS сервис не получает трафик |
| Сервис ↔ PostgreSQL / ClickHouse / Elastic | TLS 1.2+ | `sslmode=verify-full`; SASL для брокеров | Vault PKI | Запрет незашифрованного подключения на уровне СУБД |
| CDC / стримы (Debezium → Kafka) | TLS 1.2+ + SASL/SCRAM (или mTLS) | Шифрование + аутентификация каждого соединения | Vault PKI | Обезличивание на границе ETL (Task2 §5) |
| ККМ ↔ 1С | **Замена OLE на API поверх TLS 1.2+** (Task2 ПЗ-4) | Подпись сообщений (HMAC-SHA256 / ЭЦП), сервисная учётка, контроль потока | Сервисные сертификаты | Закрывает «незащищённый TCP/IP/OLE» из As-Is |
| 1С:Бухгалтерия ↔ 1С:Торговля | TLS 1.2+, шифрованный обмен (вместо OLE) | Сервисная учётка, аудит обмена | Сервисные сертификаты | ПЗ-4/ПЗ-6 |
| API с лабораторией | TLS 1.2+, **mTLS с обеих сторон** | OpenAPI-контракт с `x-data-classification`, изоляция `patient_id` | Vault PKI | ПЗ-7 (Task1) |
| Платёжный шлюз (карты/СБП) | TLS 1.2+ (треб. 4 PCI DSS) | **PAN не хранится** — токенизация (token vault эквайера); взаимная аутентификация | Сертификаты платёжной экосистемы | PCI DSS 4.0: сокращение периметра (CDE) до платёжного сервиса |
| Бухгалтерия → налоговая | TLS + **ЭЦП** (GOST R 34.10-2012 / ECDSA) | Шифрование контейнера отчёта, DLP на исходящие | Сертификат ЭЦП (токен JaCarta/USB) | Неотказуемость (R12) |
| Exchange / почта | TLS для SMTP/OWA/EWS | DLP на исходящие: блокировка `sensitivity:high` наружу | Внутренний CA / коммерческий | R9: сканы медкарт не уходят на личную почту |
| SMS / голосовой робот | API оператора поверх TLS 1.2+ | **Минимизация контента**: в SMS — только «ФИО + время», без диагнозов | — | R9, data minimization |
| Перемещение бэкапов | TLS при передаче; offline — зашифрованные носители | Ключ бэкапа отдельно от данных | — | Схема 3-2-1 |

**Сквозные требования in transit:** единый cipher policy (запрет слабых алгоритмов во всех TLS-терминаторах), HSTS, сертификаты только из Vault PKI (никаких самоподписанных в проде), мониторинг истечения (алерт за 30/7 дней), egress-фильтрация (Istio AuthorizationPolicies: трафик наружу — только в белый список).

## 6. Управление ключами (KMS)

| Функция | Инструмент | Механика |
|---|---|---|
| Хеширование/шифрование без выхода ключа | **HashiCorp Vault Transit Engine** | Envelope encryption: данные шифруются DEK, DEK шифруется KEK; KEK не покидает KMS |
| Сертификаты TLS/mTLS | **Vault PKI** | Выдача, продление, отзыв; cert-manager/Istio автоматизируют цикл |
| Секреты (учётки БД, API-ключи) | Vault Secrets Engine | Ротация по расписанию, аудит каждого доступа |
| Защита KEK | **HSM** (FIPS 140-2/3, уровень 3+) или Vault + auto-unseal с раздельным хранением Shamir-долей | ПAM-доступ (Teleport) + MFA + 4-eyes на операции с KEK |
| PAM-доступ к инфраструктуре | Teleport | Записи сессий, jump-host, запрет прямых RDP/SSH |
| Ротация | Vault (новые версии ключей Transit) | DEK: 30–180 дней по доменам; KEK: 12 месяцев; сертификаты: ≤ 90 дней |
| Отзыв / crypto-shredding | Vault + DSAR/Retention (Task2) | Уничтожение версии ключа; SLA ≤ 24 ч; событие в Audit + SIEM |
| Псевдонимизация | Vault Transit (детерминированный режим) | Токены `patient_id`; ключ ре-идентификации — отдельная привилегированная процедура с аудитом |

## 7. Автоматизированный контроль

| Что контролируется | Средство | Частота | Действие при отклонении |
|---|---|---|---|
| Теги шифрования в схемах данных (`encryption:tde+tls`, `masking`) | CI-linter (метаданные DataHub, кастомный линтер OpenAPI/миграций) — Task1 §4.3 | Каждый коммит | **Блок релиза** |
| Конфигурация TLS (протоколы, cipher suite, HSTS, ALPN) | testssl.sh / sslyze в CI + внешний скан | Ежедневно (внутренний), ежеквартально (внешний) | Алерт → инцидент, фикс ≤ 7 дней |
| Истечение сертификатов | VictoriaMetrics + Grafana (алерты 30/7/1 день) | Непрерывно | Автопродление (Vault PKI); эскалация при провале |
| Возраст ключей DEK/KEK (ротация) | Vault + CI-контроль `key age > policy` | Ежедневно | Принудительная ре-роотация, алерт |
| Операции с KMS (decrypt, ключевые версии, отзыв) | Audit-сервис (WORM) → SIEM (Elastic Security) | Непрерывно | Алерт на аномалию (UEBA): нестандартное время/объём/субъект |
| Доступ/расшифровка данных `sensitivity:high` | Audit WORM + SIEM/UEBA | Непрерывно | Алерт SOC, блокировка сессии (PAM) при подтверждении |
| Исходящая передача нешифрованных/неотмеченных ПДн | DLP (SearchInform / Microsoft Purview) на файлах и почте | Непрерывно | Блокировка отправки `sensitivity:high`, инцидент |
| Целостность и восстановимость бэкапов | Автоматический restore-тест (восстановление в изолированный стенд) | Еженедельно | Инцидент на инфраструктуру |
| Ciphertext-миграции (перезашифрование при ротации KEK) | Vault (rekey) + отчёт coverage % зашифрованных объектов | Ежеквартально | Бэклог-задача, SLA 30 дней |
| Сквозная оценка | Penetration testing (в т.ч. криптоанализ конфигураций), аудит соответствия 152-ФЗ/PCI | 1 раз в год | План корректирующих мероприятий |

**KPI зрелости шифрования (цели):**

| Метрика | Целевое значение |
|---|---|
| Доля хранилищ с at-rest шифрованием (TDE/SSE-KMS/LUKS) | 100% |

## 9. Алгоритмы и размеры ключей (сводка)

| Применение | Алгоритм | Размер ключа | Базовый стандарт |
|---|---|---|---|
| At rest: объекты, бэкапы, файлы | AES-256-GCM | 256 бит | FIPS 197/198 |
| At rest: колонки БД | AES-256-GCM (pgcrypto) | 256 бит | FIPS 197/198 |
| At rest: диски (LUKS2) | AES-256-XTS + KDF Argon2id | 256 бит | LUKS2 spec |
| In transit: внешние каналы | TLS 1.3 (AES-256-GCM / ChaCha20-Poly1305) | 256 бит | RFC 8446 |
| In transit: внутренние каналы | mTLS TLS 1.2/1.3 | 256 бит | RFC 8446 |
| Сертификаты (TLS/mTLS) | ECDSA secp256r1 (альт. RSA-3072) | 256 / 3072 бит | RFC 5480 |
| ЭЦП (налоговая, договоры) | GOST R 34.10-2012 / ECDSA | 256 бит | ГОСТ Р 34.10-2012 |
| Подпись сообщений (ККМ↔1С) | HMAC-SHA256 | 256 бит | RFC 2104 |
| Псевдонимизационные токены | AES-256-GCM (детерминированный) / HMAC-SHA256 | 256 бит | — |
| Хэширование паролей | Argon2id (альт. bcrypt) | — | RFC 9106 |
| GOST-резерв (при необходимости) | GOST R 34.12-2015 (Кузнечик), 34.10-2012, 34.11-2018 | 256 бит | ГОСТ Р 34.x |
