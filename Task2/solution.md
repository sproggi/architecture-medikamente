# Задание 2. Проектирование решения: Privacy by Design

Проектируем целевую (To-Be) систему до реализации: новые блоки в C4-архитектуре и аналитический слой, которые превентивно закрывают риски конфиденциальности, найденные в Task1 (ПЗ-1…ПЗ-10).

## 2. Принципы Privacy by Design → механизмы решения

| # | Принцип | Как реализован в проекте | Блоки |
|---|---|---|---|
| 1 | **Preventive** — профилактика, а не лечение | Threat modeling (LINDDA/STRIDE) на стадии дизайна каждого сервиса; CI блокирует релиз, если поле с тегом `pii`/`health` не имеет `masking`/`encryption` (см. Task1 §4.3) | CI-linter, DataHub |
| 2 | **Privacy by Default** — защита «из коробки» | Deny-by-default в OPA: доступ не выдан — значит запрещён; новые данные не попадают в каталог и прод без обязательных тегов; в аналитике по умолчанию только обезличенные данные | OPA, DataHub, ETL |
| 3 | **Privacy Built-in** — защита встроена | Любой сервис обращается к данным только через политики (OPA) и пишет в аудит; прямого доступа к БД извне нет (mTLS, service mesh) | OPA, Audit, Istio |
| 4 | **Full Functionality** — защита не ухудшает удобство | ABAC (свой пациент, свой филиал, смена) даёт ровно нужные данные; маскирование в UI вместо полного запрета | OPA/ABAC, маскирование |
| 5 | **End-to-End Protection** — защита всего жизненного цикла | Shifting left → шифрование при создании (TDE/KMS), TLS/mTLS при передаче, retention и **crypto-shredding** при удалении, WORM-аудит | Vault KMS, TDE, Retention, Audit |
| 6 | **Data Minimization & Segregation** — минимум данных, изоляция | Схемы форм собирают только необходимые поля; tenant isolation по `patient_id` (RLS); разделение зон raw/curated в аналитике; изоляция филиалов | Схемы форм, RLS, lakehouse |
| 7 | **Transparency & Accountability** — прозрачность | Сервис согласий, DSAR (доступ/исправление/удаление по запросу), lineage по каждому полю, аудит-логи и алерты | Consent, DSAR, DataHub, SIEM |

## 3. Риски конфиденциальности → превентивные механизмы (дизайн до реализации)

Матрица спроектирована так, что каждый риск имеет механизм, встроенный в архитектуру, а не зависящий от дисциплины людей:

| № | Риск | Сценарий | Превентивный механизм (зашит в проект) | Блок |
|---|---|---|---|---|
| R1 | Неправомерное раскрытие | Врач/ресепшен открывает чужого пациента | Deny-by-default + RLS по `patient_id`/филиал/смена; маскирование чужих записей в UI | OPA, PostgreSQL RLS |
| R2 | Массовая утечка через учётку | Компрометация AD = доступ ко всем медкартам | MFA, запрет «домен = всё», least privilege, PAM-доступ к инфраструктуре | Keycloak, Vault |
| R3 | Персонификация в аналитике | PII в озере → re-identification в BI/ML/LLM | Обезличивание на границе ETL, раздельные зоны raw/curated, ключи де-персонификации не хранятся в аналитической зоне | ETL, MinIO Object Lock, Vault |
| R4 | Дублирование данных | Excel+1С: копии PII, расхождения | Единый источник (БД/1С клиент-сервер), адаптеры, запрет ручного двойного учёта | Адаптеры 1С/ККМ |
| R5 | Избыточное хранение | Данные хранятся дольше цели / после запроса на удаление | Политики retention + автоудаление/crypto-shredding, DSR-процесс по запросу (ст.21 152-ФЗ) | Retention, DSAR |
| R6 | Отслеживание/неаудируемость | Невозможно ответить «кто читал медкарту» | Обязательный аудит C/R/U/D в WORM-хранилище, события в SIEM | Audit, Elastic |
| R7 | Непреднамеренный misflow | Данные уходят не туда (email, интеграция) | API-контракты `x-data-classification`, mTLS, DLP на почте/файлах, egress-фильтрация | API GW, DLP, Istio |
| R8 | Согласие не собрано/не отозвано | Правовой риск (ст.6, 9 152-ФЗ) | Сервис согласий: хранение, версионирование, остановка обработки при отзыве | Consent, DSAR |
| R9 | Утечка через почту/файлы | Сканы медкарт уходят на личную почту | DLP-классификация файлов и писем, блокировка отправки `sensitivity:high` наружу | DLP |
| R10 | Утечка через ML/LLM | PII в обучающих данных и ответах LLM | Обучение только на curated-зоне (обезличенные), DLP на выводах LLM, теги `consent` | ML/LLM gateway, DataHub |
| R11 | Угроза изнутри | Злостный сотрудник выгружает базу | UEBA на нетипичное поведение, квоты на выгрузки, маскирование, мгновенные алерты | SIEM/UEBA |
| R12 | Нарушение целостности | Подмена/искажение медкарты, чека | Версионирование записей, WORM-логи, фискализация ККМ, сверка 1С↔ККМ | Audit, ККМ, 1С |

## 4. Новые блоки в C4-архитектуре

Диаграммы:
- **`c4_level1_context.drawio`** — контекст системы: пользователи, внешние системы, границы платформы.
- **`c4_level2_containers.drawio`** — контейнеры платформы; **оранжевым выделены новые блоки Privacy by Design**, которые обслуживают «многие блоки» системы централизованно (cross-cutting).

### 4.1. Перечень новых блоков

| Блок | Тип | Назначение | Принципы P2D | Риски |
|---|---|---|---|---|
| **Identity Provider (Keycloak)** | Идентификация | SSO, MFA, роли/группы для всех порталов и сервисов | 1, 2, 5, 7 | R2 |
| **Policy Service (OPA)** | Авторизация | Централизованные политики RBAC+ABAC; решения на основе тегов данных; deny-by-default | 1, 2, 3, 4 | R1, R11 |
| **Data Catalog & Tagging (DataHub)** | Гигиена данных | Реестр данных, классификация, теги (`class`, `sensitivity`, `retention`, `consent`), Data Lineage | 1, 2, 6, 7 | R3, R4, R10 |
| **KMS (HashiCorp Vault)** | Криптография | Ключи TDE/файлового шифрования, сертификаты mTLS, секреты, токены псевдонимизации, PAM-доступ | 5 | R2, R3 |
| **Обезличивающий сервис (tokenization/pseudonymization)** | Трансформация | Псевдонимизация `patient_id`, маскирование, crypto-shredding | 5, 6 | R3, R5 |
| **Consent Service** | Согласия | Сбор, версионирование и хранение согласий; флаг `consent` в тегах данных | 7 | R8 |
| **DSAR Service** | Права субъекта | Запросы пациента: доступ, исправление, удаление/прекращение обработки (ст.21 152-ФЗ) | 5, 7 | R5, R8 |
| **Audit Service (WORM)** | Аудит | Неизменяемые логи C/R/U/D по данным `sensitivity:high`, передача в SIEM | 7 | R6, R11, R12 |
| **DLP (SearchInform/Purview)** | Контроль периметра | Классификация и блокировка отправки чувствительных файлов/писем наружу | 5, 6 | R9 |
| **SIEM/UEBA (Elastic Security)** | Мониторинг | Корреляция событий, алерты на нетипичные действия и несанкционированный доступ, оповещения команде | 1, 7 | R6, R11 |
| **Retention Manager** | Жизненный цикл | Политики хранения: автоудаление/архивация/crypto-shredding по тегу `retention` | 5, 6 | R5 |
| **API Gateway (Kong) + Istio mTLS** | Ввод данных | Единая точка входа: валидация OpenAPI-контрактов (`x-data-classification`), mTLS между сервисами, квоты, аудит запросов | 1, 2, 3, 6 | R7 |

**Как блоки обеспечивают Privacy by Design «во многих блоках» системы:** каждый бизнес-сервис (запись, CRM, медкарта, оплаты, лаборатория, уведомления) не реализует защиту сам — он вызывает OPA для авторизации, пишет в Audit, получает ключи из Vault, публикует метаданные в DataHub и публикует события в Kafka (на аналитику). Защита факторизована в общие блоки — изменение политики (новая роль, новый тег, новый retention) не требует переделки сервисов (НФТ: конфигурируемость, сопровождаемость).

## 5. Аналитический слой (lakehouse) с Privacy by Design

Диаграмма: **`analytics_layer.drawio`**. Цель — закрыть бизнес-потребность №2 (BI/ML/AI/LLM по данным) без переноса PII в аналитику.

### 5.1. Зоны и принцип сегрегации

| Зона | Хранение | Данные | Доступ | P2D-механизмы |
|---|---|---|---|---|
| **Raw** | MinIO с Object Lock (WORM), шифрование KMS | Оригиналы из источников (в т.ч. PII) | Только ETL-сервис; аналитикам недоступна | Segregation, End-to-end (шифрование + WORM), Lineage |
| **Curated / Analytics** | ClickHouse (OLAP), датасеты с тегами | **Только обезличенные/агрегированные**: `patient_id` (псевдоним), обобщённые значения | Аналитики, DS через Superset/ML; прямой SQL — deny-by-default | Minimization (селекция полей в ETL), Pseudonymization, Privacy by Default |
| **Serving** | Superset, JupyterHub+MLflow, LLM gateway | Отчёты, модели, ответы LLM | Роль аналитика/DS; DLP на выгрузках | Transparency (lineage до источника), DLP, consent-контроль |

### 5.2. Механизмы P2D в аналитическом слое

1. **Обезличивание на границе** (принцип 6): оператор ETL на входе заменяет прямые идентификаторы (ФИО, телефон, email, дату рождения) на псевдонимы; ключи псевдонимизации — в Vault, в аналитическую зону не попадают. Re-identification — отдельная прерогатива через сервис с аудитом (не инструмент аналитика).
2. **Минимизация** (принцип 6): в ETL-маппинге явно перечислены поля; «полные дамп БД в озеро» запрещены. Поля, не прошедшие маппинг, в oзеро не попадают.
3. **Privacy by Default** (принцип 2): таблица/датасет без тегов в DataHub не публикуется в каталог; обучение ML/LLM возможно только на curated-зоне.
4. **Lineage и прозрачность** (принцип 7): каждый ETL-шаг фиксирует происхождение (DataHub): любой BI-индикатор прослеживаем до источника и трансформаций — требование к отчётам и ответам регулятору.
5. **Контроль выгрузок** (принципы 5, 6): DLP на отчётах и выгрузках из Superset/Jupyter; LLM gateway не принимает на вход и не отдаёт данные с тегами `pii`/`health` (защита от утечки через модель — R10).
6. **Аудит запросов** (принцип 7): ClickHouse query log и логи Superset → SIEM; UEBA на нетипичные объёмы выборки (R11).
7. **Retention** (принцип 5): разные сроки по зонам (raw — 5 лет с crypto-shredding, агрегаты — бессрочно); удаление raw-объекта = crypto-shredding (уничтожение ключа), без переписи данных.
8. **Качество и целостность** (принцип 1): проверки качества (Great Expectations) в пайплайне — аналитика строится на верифицированных данных.

### 5.3. Источники данных в слой

| Источник | Способ доставки | Обработка на границе |
|---|---|---|
| PostgreSQL (портал, CRM, медкарты, записи) | CDC (Debezium) → Kafka | Псевдонимизация в реальном времени |
| 1С:Бухгалтерия / Торговля (клиент-сервер) | Адаптер (выгрузка) → Kafka | Обезличивание кадровых/ПДн сотрудников до агрегатов |
| Лаборатория | API (push, контракт `x-data-classification`) | Тегирование `class:health`, псевдонимизация |
| Сканы медкарт/договоров (MinIO) | S3-sync в raw-зону | В аналитику — только метаданные и агрегаты (не содержимое) |
| Legacy Excel (журналы, реестры) | Разовая миграция (Airbyte) | Обезличивание при миграции + lineage `lineage:excel-*` |

## 6. Сценарии работы механизмов

**С1. Врач открывает пациента (портал).**
SSO (Keycloak, MFA) → OPA: роль `doctor` + ABAC `own_patient` + филиал + `consent:required` → сервис медкарты → PostgreSQL с RLS (фильтр по `patient_id`) → запись в Audit (WORM) → событие в SIEM. Чужой пациент: запись показана в зашифрованном/замаскированном виде, попытка прямого обращения — алерт.

**С2. Пациент через мобильное приложение.**
Пациент видит **только свои** данные (анализы, заключения, договор): tenant isolation по `patient_id`, API-контракты скрывают конфиденциальные категории, которые пациенту не положено видеть; канал TLS, push-уведомления о записи, подтверждение/отмена с уведомлением ресепшена.

**С3. Аналитик строит P&L / ABC-анализ.**
Superset (RBAC) → ClickHouse curated: только обезличенные данные (`patient_id`, обобщения); lineage в DataHub показывает происхождение индикатора; выгрузка отчёта проверяется DLP; объём выборки уходит в UEBA. Для отчёта «по конкретному пациенту» — отдельная заявка через DSAR-подобный процесс с аудитом (не self-service).

**С4. Пациент требует удалить данные (ст.21 152-ФЗ).**
DSAR-сервис: верификация личности → поиск данных по `patient_id` через каталог (DataHub) → удаление из OLTP/файлов (crypto-shredding ключа), в raw-зоне — отзыв ключа; в аналитике обезличенные записи остаются (они не персонифицируемы без ключа); результат и аудит — пациенту и регулятору.

## 7. Соответствие НФТ

| НФТ | Как обеспечено |
|---|---|
| Безопасность (конфиденциальность) | Разделы 2–6: шифрование на всём цикле, минимизация, retention, удаление по запросу |
| Масштабируемость | Kubernetes, микросервисы на стеке техдиректора (Java, Postgres, ClickHouse, Elastic, VictoriaMetrics), горизонтальное масштабирование сервисов и аналитики, изоляция филиалов (ABAC) |
| Сопровождаемость | Факторизация защиты в общие блоки; контракт-файрст (OpenAPI + `x-data-classification`); CI-проверки тегов |
| Конфигурируемость | Политики в OPA/теги в DataHub/retention — меняется конфигурацией без доработки кода сервисов |
