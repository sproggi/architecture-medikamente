# Защита данных, тегирование и меры

## 1. Конфиденциальные данные, не учтённые во внутренних системах

Данные, которые компания собирает и/или обрабатывает, но для которых во внутренних системах нет реестра, владельца, аудита и сроков хранения:

| № | Данные | Где обрабатываются | Почему «не учтены» | Класс | Меры (см. §4–§5) |
|---|---|---|---|---|---|
| 1 | Жалобы и анамнез (устный приём) | Приём, бумажные формы | Не попадают ни в один журнал/систему, только в сканах | Особая категория (ст.10 152-ФЗ) | Ведение в БД, тег `class:health`, аудит |
| 2 | Согласия на обработку (в т.ч. спецкатегорий) | Бумага / не собираются | Нет реестра согласий и механизма отзыва (ст.6, 9, 21 152-ФЗ) | PII + особая категория | Сервис согласий, хранение в БД, DSR-процесс |
| 3 | Данные расширенной формы (адрес прописки, место работы/учёбы) | Excel Patients | Нет цели обработки, срока хранения, привязки к согласию | PII | Минимизация, теги, retention |
| 4 | Устные/телефонные заключения врачей | Телефон, разговор | Не фиксируются ни в одной системе | Особая категория | Фиксация в БД/сканах с KMS, аудит |
| 5 | PII и данные о здоровье в переписке | Exchange (почта) | Нет DLP, классификации, аудита исходящих сообщений | PII + здоровье | DLP, теги, аудит, маскирование |
| 6 | Бумажные медкарты, согласия, заявки | Бумага | Сканы не связаны с пациентом и системой (нет реестра) | Особая категория | Скан с KMS, реестр «скан ↔ пациент», DLP |
| 7 | Сканы договоров и медкарт на общем диске | Файловый сервер | Не инвентаризированы, нет владельца и retention | PII + особая категория | Инвентаризация, KMS (AES-256), retention |
| 8 | ПДн сотрудников (кадры, зарплаты) | 1С:Бухгалтерия | Нет реестра данных, минимизации, разграничения | PII сотрудников | TDE, RBAC, маскирование сумм |
| 9 | Платежи без привязки к пациенту | ККМ, Excel, 1С | Платёж и пациент связаны только вручную; двойной учёт | Финансы + PII | Единый источник, API ККМ, сверка, аудит |
| 10 | Заявки на анализы (с PII пациента) | Excel → лаборатория | Передаются без API-контракта; не зафиксировано, кто запрашивал и кто видел | PII + здоровье | API-контракт `x-data-classification`, изоляция `patient_id`, аудит |

**Вывод:** пункты 1, 2, 4, 10 — данные без цифрового учёта в системах; 3, 5, 6, 7 — есть, но без контроля; 8, 9 — в системах, но без учёта. Все подлежат включению в реестр, тегированию и аудиту доступа.

## 2. Аудит текущих мер безопасности (As-Is)

Существующие меры и их достаточность:

| № | Существующая мера | Где применяется | Оценка |
|---|---|---|---|
| 1 | Доменная аутентификация AD/LDAP (Windows Server 2022) | Сеть, файловый сервер, почта, 1С | ❌ Недостаточно: нет MFA, нет RBAC/ABAC — компрометация учётки AD = доступ ко всем медкартам (ПЗ-9) |
| 2 | Файловый сервер с общими папками | Материалы, Excel, сканы | ❌ Доступ у любого сотрудника с учёткой; нет аудита действий (ПЗ-2, ПЗ-3) |
| 3 | 1С в файловом режиме | Платежи, кадры, ТМЦ | ❌ Единый файл, нет серверного контроля доступа, нет отказоустойчивости (ПЗ-8) |
| 4 | ККМ ↔ 1С (TCP/IP + OLE) | Приём платежей | ❌ Канал не зашифрован, сообщения не подписаны (ПЗ-4) |
| 5 | Exchange Mail Server | Внутренняя переписка | ❌ Нет DLP, нет аудита исходящих, классификации сообщений |
| 6 | Windows Server 2022 (AD, DNS, DHCP) | Инфраструктура | ⚠️ Нет данных об аптайме, патчах и hardening — требует доаудита |
| 7 | Физический сервер на территории офиса | Всё | ⚠️ Локализация ПДн (152-ФЗ) соблюдена, но единая точка отказа; резервное копирование не подтверждено — риск для доступности (5C) |

**Полностью отсутствуют меры:** MFA, PAM, шифрование at-rest, шифрование in-transit на бизнес-каналах, DLP, SIEM/UEBA, аудит доступа, Data Lineage, retention и удаление, учёт согласий, RBAC/ABAC, API-контракты, маскирование/обфускация, обезличивание.

**Вывод:** единственная существующая мера — идентификация (доменная аутентификация) — не обеспечивает требований ст.18.1 и ст.19 152-ФЗ для данных особой категории. Полный набор целевых мер — в §3 (список данных), §4 (тегирование), §5 (меры по потокам) и на To-Be диаграммах.

## 4. Механизм тегирования данных

### 4.1. Таксономия тегов

| Тег | Значение | Допустимые значения | Пример |
|---|---|---|---|
| `class` | Класс данных | `pii`, `health`, `financial`, `secret`, `meta` | `class:health` |
| `sensitivity` | Уровень чувствительности | `high`, `med`, `low` | `sensitivity:high` |
| `retention` | Срок хранения | ISO-8601 или `5y`, `1y`, `0` | `retention:5y` |
| `owner` | Домен-владелец | `medical`, `finance`, `hr`, `it` | `owner:medical` |
| `lineage` | Происхождение данных | источник | `lineage:excel-journal` |
| `consent` | Требуется согласие субъекта | `required`, `not_required` | `consent:required` |
| `encryption` | Требуемое шифрование | `tde`, `kms`, `tls`, `tde+tls` | `encryption:tde+tls` |
| `masking` | Требуемое маскирование | `ui`, `logs`, `none` | `masking:ui` |
| `rbac` | Роли с доступом | список ролей | `rbac:doctor,admin` |
| `abac` | Атрибуты доступа | список атрибутов | `abac:branch,shift` |

### 4.2. Инструменты тегирования

| Инструмент | Назначение | Где применять |
|---|---|---|
| **DataHub / OpenMetadata / Apache Atlas** | Data Catalog, теги на таблицы/колонки/файлы, Data Lineage | Озеро данных, БД, Excel-источники |
| **Microsoft Purview / SearchInform DLP** | Автоклассификация по шаблонам (ФИО, СНИЛС, диагноз), DLP-теги | Файлы на диске, почта, сканы |
| **OpenAPI `x-data-classification`** | Теги в API-контрактах | Лаборатория, портал, платёжный шлюз |
| **PostgreSQL `COMMENT ON` / ClickHouse column comments** | Теги на уровне колонок БД | БД порталов, озеро |
| **S3/Object Storage object tags / Elastic metadata** | Теги на объекты и документы | Файловое хранилище, Elastic |
| **Git + CI (custom linter)** | Проверка тегов в коде и миграциях | Релизы |
| **SIEM (Elastic Security / Wazuh) + UEBA** | Потребление тегов для алертинга | Мониторинг |

### 4.3. Правила тегирования

1. **Обязательность:** любое новое поле/файл/эндпоинт при создании получает минимум `class`, `sensitivity`, `owner`. Без тегов — блокировка публикации в CI.
2. **Автоправила:** `class:health` → автоматически `sensitivity:high`, `encryption:tde+tls`, `masking:ui`, `rbac:doctor`, `retention:5y`, `consent:required`.
3. **CI-валидация:** если в OpenAPI/схеме БД есть поле с `class:pii`/`class:health` без `masking` или `encryption` — сборка падает.
4. **Data Lineage:** каждый ETL-шаг обязан проставлять `lineage:<источник>`; в озере данные без lineage не публикуются.
5. **Мониторинг:** теги `sensitivity:high` передаются в SIEM; доступ к ним генерирует событие аудита и алерт при нетипичном поведении.
6. **Retention:** по истечении `retention` — автоматическое удаление или архивирование с уведомлением владельца домена.

### 4.4. Пример применения (YAML-манифест поля)

```yaml
field: patient_diagnosis
table: medical.cards
tags:
  class: health
  sensitivity: high
  retention: 5y
  owner: medical
  lineage: excel-pacient-card
  consent: required
  encryption: tde+tls
  masking: ui
  rbac: [doctor]
  abac: [branch, shift, own_patient]
```

## 5. Инструменты, способы и меры обеспечения конфиденциальности по потокам

### 5.1. Сводная таблица мер по потокам

| № | Поток | Данные | Меры |
|---|---|---|---|
| 1 | Пациент → ресепшен (запись) | PII, жалобы | TLS 1.2+, минимизация полей формы, маскирование в UI, RBAC (ресепшен — свой филиал), ABAC (смена), аудит |
| 2 | Ресепшен → журнал записи | PII + здоровье | Замена Excel на БД с TDE, теги `class:pii`/`class:health`, аудит C/R/U/D, версионирование, бэкапы с шифрованием |
| 3 | Ресепшен → медкарта/сканы | Особая категория | Шифрование файлов (KMS, AES-256), DLP (SearchInform/Purview), RBAC (врач — свой пациент), аудит доступа, WORM-логи |
| 4 | Ресепшен → договор | PII + коммерческая | TDE + TLS, маскирование сумм в логах, ABAC (филиал), retention |
| 5 | Кассир → ККМ | Финансы + PII | TLS на канале, фискализация, маскирование PAN, аудит |
| 6 | ККМ → 1С (TCP/IP + OLE) | Финансы + PII | Замена OLE на защищённый API/TLS, подпись сообщений, сервисная учётка, контроль потока, аудит |
| 7 | Кассир → Excel (двойной учёт) | Финансы | Устранение дублирования, единый источник (1С/БД), сверка, отказ от Excel |
| 8 | 1С:Бухгалтерия ↔ 1С:Торговля (OLE) | Финансы, ТМЦ | Шифрованный канал, сервисная учётка, аудит обмена, переход на клиент-серверный режим 1С |
| 9 | Бухгалтерия → налоговая | PII сотрудников | Шифрование документов, ЭЦП, DLP, TLS |
| 10 | Лаборатория → реестры анализов | Особая категория | API-контракты с `x-data-classification`, изоляция по `patient_id`, TLS, аудит, теги `class:health` |
| 11 | Врач → журнал/заключения | Особая категория | RBAC/ABAC (свой пациент, филиал, смена), аудит, маскирование чужих пациентов |
| 12 | Врач → лабораторные реестры | Особая категория | Изоляция patient_id, RBAC, аудит, запрет на чтение чужих записей |
| 13 | AD/LDAP/Exchange | Учётные данные | MFA, PAM (Teleport / HashiCorp Vault), аудит, ротация секретов, условный доступ |
| 14 | Excel/сканы → озеро данных | Производные PII | ETL с обезличиванием, Data Lineage (Atlas/DataHub), теги, KMS, разделение зон raw/curated |
| 15 | Озеро → BI/ML/AI/LLM | Производные PII | Только обезличенные/агрегированные данные, теги `class:*`, контроль LLM-обучения, DLP на выгрузки |
| 16 | Мониторинг/алертинг | Метаданные | SIEM (Elastic Security / Wazuh), алерты на доступ к `sensitivity:high`, UEBA, WORM-хранение логов |

**Сквозные меры:** классификация + теги, RBAC/ABAC, KMS/шифрование (TDE, TLS, файловое), DLP, SIEM/UEBA, аудит и Data Lineage, политика retention и удаления, MFA/PAM, Privacy By Design в CI, резервное копирование с шифрованием.

### 5.2. Детализация по потокам: инструменты, способы, меры

#### Поток 1. Пациент → ресепшен (запись на приём)
- **Данные:** ФИО, ДР, телефон, email, жалобы.
- **Инструменты:** TLS-терминатор (nginx/HAProxy), WAF, форма с минимизацией полей, RBAC/ABAC в приложении, аудит-лог.
- **Способы:** TLS 1.2+, минимизация, маскирование в UI, ограничение по филиалу/смене.
- **Меры:** аутентификация сотрудника, MFA для ресепшена, журналирование C/R/U/D.

#### Поток 2. Ресепшен → журнал записи
- **Данные:** PII + данные о здоровье (жалобы).
- **Инструменты:** PostgreSQL с TDE (pgcrypto / шифрование диска), DataHub-теги, SIEM.
- **Способы:** замена Excel на БД, версионирование, бэкапы с шифрованием.
- **Меры:** `class:pii`/`class:health`, аудит C/R/U/D, retention, RBAC.

#### Поток 3. Ресепшен → медкарта/сканы
- **Данные:** особая категория ПДн.
- **Инструменты:** KMS (HashiCorp Vault / AWS KMS), DLP (SearchInform / Microsoft Purview), WORM-хранилище логов.
- **Способы:** шифрование файлов AES-256, DLP на выгрузки, RBAC «врач — свой пациент».
- **Меры:** аудит доступа, маскирование чужих записей, retention, согласие.

#### Поток 4. Ресепшен → договор
- **Данные:** PII + коммерческая тайна.
- **Инструменты:** TDE, TLS, DLP, ABAC-движок.
- **Способы:** маскирование сумм в логах, ABAC (филиал), retention.
- **Меры:** аудит, теги `class:pii+financial`.

#### Поток 5. Кассир → ККМ
- **Данные:** финансы + PII.
- **Инструменты:** TLS на канале, фискализация, маскирование PAN.
- **Способы:** tokenization PAN, аудит операций.
- **Меры:** RBAC кассира, аудит, контроль смены.

#### Поток 6. ККМ → 1С (TCP/IP + OLE)
- **Данные:** финансы + PII.
- **Инструменты:** TLS-прокси, подпись сообщений, сервисная учётка, SIEM.
- **Способы:** замена OLE на защищённый API/TLS, контроль потока.
- **Меры:** аудит обмена, ротация сервисной учётки.

#### Поток 7. Кассир → Excel (двойной учёт)
- **Данные:** финансы.
- **Инструменты:** единый источник (1С/БД), сверка, DLP.
- **Способы:** устранение дублирования, отказ от Excel.
- **Меры:** сверка, аудит, контроль расхождений.

#### Поток 8. 1С:Бухгалтерия ↔ 1С:Торговля (OLE)
- **Данные:** финансы, ТМЦ.
- **Инструменты:** шифрованный канал, сервисная учётка, SIEM.
- **Способы:** переход на клиент-серверный режим 1С, шифрованный обмен.
- **Меры:** аудит обмена, RBAC.

#### Поток 9. Бухгалтерия → налоговая
- **Данные:** PII сотрудников.
- **Инструменты:** ЭЦП, TLS, DLP.
- **Способы:** шифрование документов, ЭЦП, DLP на выгрузки.
- **Меры:** аудит, RBAC бухгалтерии.

#### Поток 10. Лаборатория → реестры анализов
- **Данные:** особая категория.
- **Инструменты:** API Gateway, OpenAPI `x-data-classification`, TLS, DataHub.
- **Способы:** API-контракты, изоляция по `patient_id`, теги `class:health`.
- **Меры:** аудит, RBAC/ABAC, retention.

#### Поток 11. Врач → журнал/заключения
- **Данные:** особая категория.
- **Инструменты:** RBAC/ABAC-движок, аудит-лог, KMS.
- **Способы:** RBAC «свой пациент», ABAC (филиал, смена), маскирование чужих записей.
- **Меры:** аудит, теги `class:health`, retention.

#### Поток 12. Врач → лабораторные реестры
- **Данные:** особая категория.
- **Инструменты:** изоляция patient_id, RBAC, аудит.
- **Способы:** запрет чтения чужих записей, маскирование.
- **Меры:** аудит, теги, retention.

#### Поток 13. AD/LDAP/Exchange
- **Данные:** учётные данные.
- **Инструменты:** MFA (Duo / Microsoft Entra), PAM (Teleport / HashiCorp Vault), SIEM/UEBA.
- **Способы:** MFA, PAM, ротация секретов, условный доступ.
- **Меры:** аудит, алерты на нетипичные действия.

#### Поток 14. Excel/сканы → озеро данных
- **Данные:** производные PII.
- **Инструменты:** ETL (Airbyte / NiFi), DataHub/Atlas, KMS, DLP.
- **Способы:** обезличивание на ETL, Data Lineage, теги, разделение raw/curated.
- **Меры:** аудит, retention, контроль доступа к raw-зоне.

#### Поток 15. Озеро → BI/ML/AI/LLM
- **Данные:** производные PII.
- **Инструменты:** BI (Superset/Metabase), ML-платформа, DLP на выгрузки.
